# 架构可视化（Arch Map）

## 第一步：扫描并理解项目结构

1. 列出项目根目录的一级目录（跳过 .git、构建产物目录）
2. 识别分层：按目录结构判断架构层（如 ASW/BSW/Core/Drivers、src/、lib/ 等）
3. 用 glob 统计各层/各模块的源文件数，找出空模块（有目录无文件）

## 第二步：分析模块依赖

1. 抽查每层关键模块的源文件，收集 `#include` 关系（C/C++ 项目）或 import 语句
2. 确定依赖方向：谁 include 谁；标记"装配中心"（被最多模块依赖的入口，如 main.c）
3. 区分：业务模块间依赖 / 对公共头文件的依赖 / 对底层驱动库的依赖

## 第三步：输出架构图（Mermaid 优先）

用 Mermaid `graph TB` 生成分层架构图：
- 每个架构层一个 subgraph，层内是模块节点
- 模块间依赖画有向边，标注关键依赖
- 空模块标注"(空)"
- 若界面不渲染 Mermaid，同时输出等价的文字树状结构图

## 第四步：追踪本次任务改动（核心）

1. **从任务开始**，每次调用 write/edit 工具写文件后，把该文件路径记入"改动清单"
2. 将每个改动文件映射到所属模块（路径 → 层/模块）
3. 任务结束时（或用户要求时）输出：

   **① 改动高亮图**：在架构图上用醒目方式标记本次动过的模块：
   - 高亮样式：`classDef modified fill:#ff6b6b,stroke:#c92a2a,stroke-width:3px`（红色填充 + 粗红边框）
   - 节点文字加标记：被改动模块名标注 `🔴`（如 `AU515["🔴 au515.c"]`）
   - 未改动模块保持默认样式，形成强对比
   - 输出文字树状图时，在改动模块行尾加「🔴 本次改动」

   **② 改动清单**：列出 文件 → 模块 → 改动性质（新增/修改/删除）

   **③ 影响分析**：根据依赖关系说明——改动影响谁、谁依赖它、
   是否跨层（如业务层直接改了驱动层 = 架构信号，要提醒用户）

## 注意

- 只读扫描，不修改任何项目文件
- 若项目结构异常复杂，先输出模块级图，再按需下钻
